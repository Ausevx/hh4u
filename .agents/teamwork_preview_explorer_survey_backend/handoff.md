## 2. Logic Chain

1. **Premise 1 (Observation 1.1 & 1.2):** The 184 `Level1Question` documents currently in MongoDB Atlas contain synthetic pseudo-random embedding vectors generated by `MockEmbeddingService` (cosine similarity = 1.0000 to the deterministic mock algorithm).
2. **Premise 2 (Observation 1.3):** At runtime, `aiContainer.ts` uses `process.env.GEMINI_API_KEY` to instantiate `GeminiEmbeddingService`. Incoming queries (e.g. "vomiting", "headache") are converted to live 1536-dimensional semantic vectors by Google Gemini (`gemini-embedding-2`).
3. **Premise 3 (Observation 1.2 & 1.3):** Real Gemini semantic embedding vectors have zero correlation with Mulberry32 pseudo-random mock vectors (cosine similarity 0.0347 to 0.0833). Atlas maps this to a maximum score of 0.5417.
4. **Premise 4 (Observation 1.3):** Because 0.5417 is below `DEFAULT_MATCH_CONFIDENCE_THRESHOLD = 0.75`, `chatbotService.ts` flags every query as non-confident (`matchConfident = false`) and falls back to conversational LLM responses. No remedy answers are ever returned.
5. **Premise 5 (Observation 1.4):** When the questions are embedded with Gemini API, cosine similarity for "vomiting" is 0.7871 (Atlas score 0.8936) and for "headache" is 0.7832 - 0.8136 (Atlas score 0.8916 - 0.9068), well above 0.75.
6. **Inference:** Therefore, the cause of queries returning no results is the vector space mismatch between live query embeddings (Gemini) and stored document embeddings (Mock). Backfilling the stored documents with real Gemini embeddings directly resolves the issue.
7. **Premise 6 (Observation 1.5):** The bulk upload endpoint only performs upserts without inspecting `mode`. Supporting `mode: 'append' | 'overwrite'` requires extracting `req.body.mode` (or `req.query.mode`) in `adminKnowledgeBaseController.ts` and conditionally executing `deleteMany({})` on `Level1Question`, `ConsultationQuery`, and `Answer` before inserting in `adminKnowledgeBaseService.ts`.

## 3. Caveats

- **Gemini API Rate Limits (429):** Generating embeddings for all 184 questions simultaneously via `Promise.all` causes 429 quota exhaustion. The backfill and bulk upload must process documents in batches of 10 with a ~300ms pause between batches.
- **Atlas Search Asynchrony:** Index creation on Atlas is asynchronous. If the index does not exist, submitting creation with `waitForReady: false` during startup allows the server to bind its port without blocking.
- **MongoMemoryServer in Offline CI:** In local/offline tests (e.g., `MongoMemoryServer`), Atlas `$vectorSearch` is not supported. `vectorSearchService.ts` correctly falls back to in-memory cosine ranking.
- **LLM Candidate Models:** In `geminiLLMService.ts`, `candidateModels` includes non-existent names (`gemini-3.6-flash`, `gemini-3.5-flash`, `gemini-3.8-flash`) that return 503 and cause slow retry loops. Adding valid models (`gemini-2.5-flash`, `gemini-2.0-flash`, `gemini-1.5-flash`) eliminates this delay.

## 4. Conclusion

1. **Diagnosis:** Queries like "vomiting" and "headache" return no results because MongoDB Atlas holds `MockEmbeddingService` vectors while runtime queries generate `GeminiEmbeddingService` vectors, resulting in low similarity scores (~0.54) that fail the 0.75 confidence threshold.
2. **Remedy:**
   - Implement `vectorBackfillService.ts` to detect mock/missing embeddings and re-generate live Gemini embeddings in batches of 10.
   - Hook `verifyAndInitializeVectorPipeline()` into `src/index.ts` after database connection.
   - Expose `GET /api/admin/vector-status` for health diagnostics.
   - Expose `POST /api/admin/vector-sync` for administrative trigger.
   - Update `POST /api/admin/knowledge-base/import` and `importKnowledgeBaseFromExcel` to support `mode: 'append' | 'overwrite'`. When `overwrite` is selected, delete existing questions, consultations, and answers before inserting new ones.
